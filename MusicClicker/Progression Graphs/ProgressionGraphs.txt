Progression Graphs Report
=========================

Overview
--------
This document lists the main growth formulas used in MusicClicker, where they are defined/used in the codebase, what they do, and sample numeric progressions (tables) for a few purchase counts or typical states. Numeric samples are computed using current default base values found in `Helpers/GameState.cs` and logic in `Helpers/UpgradeManager.cs`, `Views/ArmoryOfForteScreen.axaml.cs`, and event banner screens.

Files referenced (key locations)
- Upgrade cost & effects: `Helpers/UpgradeManager.cs` (BuyUpgrade)
  - Cost formula: cost = Round(baseCost * 1.15^owned, 2)
  - Effect per purchase: +NPS (NotesPerSecond) and/or +Click (NotesPerClick)
- Base costs and initial values: `Helpers/GameState.cs` (fields like `ChordBaseCost`, `ScaleBaseCost`, initial NotesPerSecond and NotesPerClick)
- Armory (weapon) cost formula: `Views/ArmoryOfForteScreen.axaml.cs`
  - baseMultiplier = 250 * 20^(weaponIndex+1)
  - Cost formula: cost = (NotesPerSecond + baseMultiplier) * (NotesPerClick / 2)
- Event banners (DiesIrae/Winter): `Views/Event Banners/DiesIraeEventScreen.axaml.cs` and `WinterEventScreen.axaml.cs`
  - Cost formula: cost = ((NotesPerSecond * 5) * NotesPerClick) + 250
- Other fixed NPS grants: `Helpers/UniteTheSymphonyManager.cs` (large one-time NPS bonuses for crafted items)

Conventions used here
- NPS = NotesPerSecond
- NPC = NotesPerClick
- `owned` means number already bought for an upgrade slot
- We show sample tables for owned = 0..10 for upgrade slots. Numbers rounded to the same rules the game uses (costs rounded to 2 decimals; visible notes rounded to 1 decimal).

2) Armory / Weapons (very large, base dominated)
------------------------------------------------
From `Views/ArmoryOfForteScreen.axaml.cs`:
- baseMultiplier(weaponIndex) = 250 * 20^(weaponIndex + 1)
- cost = (NotesPerSecond + baseMultiplier) * (NotesPerClick / 2)

Interpretation:
- `baseMultiplier` grows by 20x per weapon index (weapon 0 → 20^1; weapon1 → 20^2; etc.). This makes higher-tier weapons vastly more expensive and dominated by the baseMultiplier rather than the player's NPS.
- NotesPerClick (NPC) scales multiplicatively: cost is proportional to (NPC / 2).

Sample using saved data default values (example saved NPS=1004.5 and NPC=1)
- weapon 0 baseMultiplier = 250 * 20^1 = 5,000
  cost = (1004.5 + 5000) * (1 / 2) = 6004.5 / 2 = 3002.25
- weapon 1 baseMultiplier = 250 * 20^2 = 100,000
  cost = (1004.5 + 100000) * 0.5 = 101004.5 * 0.5 = 50502.25
- weapon 2 baseMultiplier = 250 * 20^3 = 2,000,000
  cost ≈ (2,001,004.5) * 0.5 = 1,000,502.25

Observation: weapon costs are enormous and scale by ×20 per weapon tier; incremental NPS has negligible effect at high tiers.

3) Event banners (DiesIrae, Winter)
-----------------------------------
From `Views/Event Banners/*EventScreen.axaml.cs`:
- cost = ((NotesPerSecond * 5) * NotesPerClick) + 250

Sample (NPS = 1004.5, NPC = 1):
- cost = (1004.5 * 5 * 1) + 250 = 5022.5 + 250 = 5272.5

Effect of growth:
- Cost is linear in NotesPerSecond and NotesPerClick; doubling NPS doubles the dynamic portion (NPS*5*NPC).
- The fixed +250 makes low-NPS purchases slightly more expensive than zero.

4) Notes accumulation over time
-------------------------------
- The main game loop adds NPS * elapsedSeconds to Notes each accumulation tick (see `MainWindow.axaml.cs`):
    gameState.Notes += gameState.NotesPerSecond * elapsedSeconds;
  So Notes grows linearly with current NPS while NPS is constant. Because purchasing upgrades increases NPS discretely, Notes growth accelerates stepwise when upgrades bought.

Concrete formulas to implement (your preference respected)
-------------------------------------------------------
Per your instruction, we will *not* change how NPS or NPC themselves grow — they remain the underlying associated values. Instead, costs and gating will be computed from those values so that:
- Higher-tier weapons require significant idle time (hard to get).
- Clicking (NPC) reduces idle time but cannot fully trivialize purchases.
- Event banners use a simple, predictable formula — example you gave: Cost = NPS * 2 + (NPC * 5).

Below are implementable formulas, with default tuning parameters and sample tables. These are intentionally simple, deterministic, and safe to put into code in a single place (e.g., a new `ProgressionConfig` and small helper methods used by `ArmoryOfForteScreen` and event screens).

Parameters (defaults)
- idleBaseSeconds = 60           // base idle cost in seconds for tier 0
- idleGrowth = 6                // multiplier per weapon tier (60s, 360s, 2160s...)
- clickWeight = 50              // how many NPS-equivalent units one NPC counts for (pre-clamp)
- clickCapFraction = 0.10      // max fraction of player's NPS that clicks may substitute
- baseOffset(tier) = 0         // optional small constant per-tier (default 0)

Weapon cost formula (idle-time interpretation)
  idleSecondsTarget(tier) = idleBaseSeconds * idleGrowth^tier
  clickContribution = min(NPC * clickWeight, NPS * clickCapFraction)
  effectiveNPS = NPS + clickContribution
  cost_weapon(tier) = round(idleSecondsTarget(tier) * effectiveNPS + baseOffset(tier), 2)

Notes:
- `clickContribution` is clamped so excessive clicking cannot fully replace idle progression.
- You can choose a different diminishing-returns style (sqrt/log) for clicks, but the clamp is simplest and predictable.

Sample numeric table: NPS = 1000, NPC = 1 (defaults)
- clickContribution = min(1*50, 1000*0.10) = min(50,100) = 50
- effectiveNPS = 1050

---------------------------------------------------
You asked for two main changes:
- Make NPS upgrades start at a meaningful baseline (e.g., 5 NPS) and grow exponentially thereafter.
- Make Notes-per-Click upgrades follow a similar exponential growth rule (but balanced so clicks don't trivialize costs).

You also asked that purchasable items (weapons) be priced in a way that reflects "how long a player must idle to obtain them" and that clicks (NPC) should not let players bypass intended progression. Event banners should follow a similar progression pattern and encourage strategy.

A. Upgrade effect model (NPS and NPC)
-------------------------------------
Goal: each purchase gives a growing effect; the first purchase should be meaningful (e.g., 5 NPS), and later purchases scale up exponentially.

Formula (per-slot incremental effect):
  effect_increase(owned) = baseEffect * growth^owned
Where:
  - baseEffect is the first-purchase increase (e.g., 5 for NPS upgrades).
  - growth is the per-purchase multiplier (e.g., 1.20--1.30). A value of 1.2 gives moderate exponential growth.

Two sensible presets:
- Aggressive: baseEffect = 5, growth = 1.25
- Balanced: baseEffect_NPS = 5, growth_NPS = 1.20; baseEffect_NPC = 1, growth_NPC = 1.25

Implementation notes:
- UpgradeManager should stop taking a fixed npsIncrease/clickIncrease and instead compute effect_increase(owned) for each purchase (or per-slot base/growth parameters kept in GameState or a config table).
- Keep the cost formula (baseCost * 1.15^owned) but re-balance baseCost to match the larger effects; or optionally replace cost growth multiplier with a separate parameter (costGrowth) if you want faster or slower price escalation.

B. Cost model for weapons (idle-time target)
-------------------------------------------
Goal: weapon prices should be interpretable as “how long must the player idle (with current NPS) to earn this weapon”, while clicks can contribute only a bounded share (so players cannot click their way past progression easily).

Design parameters:
- idleSecondsTarget(tier): desired idle time to earn a weapon of `tier`. This should grow with tier (e.g., 1 minute → 5 minutes → 30 minutes → several hours). A safe geometric rule:
    idleSecondsTarget(tier) = idleBaseSeconds * idleGrowth^tier
  Example: idleBaseSeconds = 60 (1 minute), idleGrowth = 6 → [60s, 360s, 2160s, 12960s,...]

- clickCapFraction: maximum fraction of the effective NPS contribution that may come from clicking (e.g., 0.10 means clicks can at most substitute 10% of NPS contribution to weapon cost).
- clickWeight: how much a single NPC counts toward an NPS-equivalent before clamping (a tuning parameter).

Concrete formula (per weapon tier i):
  clickContribution = min(NPC * clickWeight, NPS * clickCapFraction)
  effectiveNPS = NPS + clickContribution
  cost = round(idleSecondsTarget(i) * effectiveNPS + baseOffset(i), 2)

Where baseOffset(i) is an optional static floor (small) to keep very low-tier weapons slightly non-zero when NPS ≈ 0. If you want to preserve the previous huge base multiplier scheme, you can retain a scaled baseMultiplier, but I recommend removing the enormous 20^n jumps and using idleSecondsTarget to express intended player-time directly.

Example parameters and samples (NPS=1000, NPC=1):
- idleBaseSeconds = 60, idleGrowth = 6 ⇒ idleSeconds = [60, 360, 2160, 12960]
- clickWeight = 50 (so 1 NPC ≈ 50 NPS before clamp)
- clickCapFraction = 0.10 (clicks can contribute at most 10% of NPS)

Compute clickContribution = min(1 * 50, 1000 * 0.10) = min(50,100) = 50
effectiveNPS = 1050

Costs:
- tier 0 (60s): cost = 60 * 1050 = 63,000
- tier 1 (360s): cost = 360 * 1050 = 378,000
- tier 2 (2160s): cost = 2,268,000

Interpretation: those numbers express how many seconds of idling at 1000 NPS (plus permitted click contribution) would be required to buy a weapon. Tuning idleBase and idleGrowth lets you compress or expand these time windows.

Notes on click domination and alternatives:
- Using a clamp (clickCapFraction) prevents small-NPC players from using very high click rates to trivialize purchase times.
- Alternative click dampening: use `clickContribution = sqrt(NPC) * clickScale` or `log1p(NPC) * scale`, both of which make clicks subject to diminishing returns without an explicit clamp.

C. Event banners (baseline & strategy incentives)
-------------------------------------------------
Proposed pattern: treat event banners like smaller weapons with shorter idle targets and a strategic multiplier that makes them attractive at specific milestones.

Formula example:
  idleSecondsEvent = eventIdleBase * eventIdleGrowth^tier
  clickContribution = min(NPC * clickWeightEvent, NPS * clickCapFractionEvent)
  cost = round(idleSecondsEvent * (NPS + clickContribution) * eventDifficultyMultiplier + eventBaseOffset, 2)

Tune eventDifficultyMultiplier < 1 for cheaper, > 1 for more demanding banners. Because event banners should reward strategy, consider adding requirement components (e.g., "requires owning X weapons" or "gives bonus only to certain builds") rather than only price changes.

D. Implementation guidance
---------------------------
- Make the effect calculation pluggable (function or small table per upgrade type) so you can tune `baseEffect` and `growth` at runtime/config without touching core logic.
- Keep cost scaling separate from effect scaling. That lets you iterate: e.g., larger effect with slower cost growth or smaller effect with faster cost growth.
- For click influence on costs, prefer a diminishing-returns function (sqrt/log) or an explicit clamp (clickCapFraction) for predictable behavior.
- Add developer configuration in `GameState` or a new `ProgressionConfig` static class with named tuning parameters (idleBaseSeconds, idleGrowth, clickWeight, clickCapFraction, baseEffect per slot, growth per slot). That allows live tuning without code changes.

E. Backwards compatibility / saves
---------------------------------
- Changing base effects and cost formulas will alter existing save balance. Consider adding a `saveVersion` integer to `GameState` and a migration path that either:
  1) Recomputes player-equivalent progress into the new system (hard); or
  2) Leaves existing owned counts and notes, but ensure new formulas apply going forward (recommended for simpler rollout).
